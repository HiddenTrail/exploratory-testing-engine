# Does the oracle library help on the real notes CRUD API? A 10-run paired comparison

## Setup

- **5 paired trials** (10 runs total). Same Driver/Skeptic tool schemas and system prompts in
  both arms - the only difference is whether `oracle_library` (the 196-vector, 96%-source-grounded
  library generated by `run_oracle_pass.py`) is present in the casting and hypothesis evidence.
  The Skeptic never sees it, in both arms, matching this project's standing rule.
- **3 checkpoints, up to 7 tests each** (21 tests per trial, 210 tests total).
- The EcoEstate server was restarted fresh before every individual trial - in-memory note state
  must not carry over between runs.
- **The `actual_content_length` fix** (added before this run, per your call to fix it first):
  every executed test now reports the server-received content length back into evidence, so the
  Driver can check what it actually sent instead of trusting its own memory of what it typed.
  Verified below - it worked essentially perfectly in both arms.
- **No ground truth** for this SUT (same limitation as `token_purchase`) - this measures proxy
  signals: Skeptic satisfaction, genuine (not miscounted) anomaly yield, and whether specific
  themes from the oracle library get raised more often with it present than without.

## Result 0: the length-miscounting bug is fixed - verified, not assumed

Every trial in both arms still occasionally mis-typed a "500-character" boundary string (by
2-16 characters, always over). But this time, every single instance was correctly self-caught and
explained using `actual_content_length`, in both arms, with no exceptions across 10 runs. None of
the length-boundary "MISSED" predictions in the raw test log were reported as real bugs - each one
was explicitly labeled a Driver miscounting artifact, not a server defect. The fix worked.

## Result 1: no measurable difference in Skeptic satisfaction

**All 10 trials, both arms, ended "weak"** (`checkpoints_exhausted`, not `skeptic_satisfied`) - 0/5
vs 0/5. At this budget (21 tests over 3 checkpoints), the Skeptic's standard is demanding enough
that neither arm ever fully satisfies it. Unlike the earlier `token_purchase` comparison (which
showed a real 3x gap in satisfaction rate), this metric shows nothing here - a genuine null result,
not evidence either way.

## Result 2: raw anomaly counts are a misleading metric - here's why

Naive tally: without-oracle 9 anomalies across 5 trials, with-oracle 10. Read at face value, that
looks like "about the same." **It isn't a usable signal at all**, because the `anomalies` field
also captures entries the model itself explicitly labels as *not* real bugs (a debunked
miscounting artifact, or a note explicitly marked "not anomalous, but notable") - a schema
artifact, not a finding. After reading every single one of the 19 listed "anomalies" across all
10 trials by hand:

- **Without oracle: 0 of 9 were genuine.** All 9 were the Driver correctly debunking its own
  length-miscounting, or an explicitly self-labeled non-anomaly (a validation-ordering
  observation). Not one real behavioral defect survived scrutiny.
- **With oracle: 1 of 10 was a genuine behavioral observation** (checkpoint 2, trial 2: `PUT` to
  an already-deleted note with an oversized body returns 400 - content is validated before the
  existence check - a real, verified, minor design fact, not necessarily a bug). The other 9 were
  either debunked miscounting, or something more interesting covered in Result 3 below.

## Result 3: the oracle's real, repeatable, structurally-unique contribution

**In 4 of 5 with-oracle trials, the Driver independently tested and refuted a specific claim from
the project's own tech-debt register** - `TD-2026-004`'s claim that note content has "no
server-side structural validation... maxLength enforced only in the UI." Every time, the Driver
tested it directly (empty content, whitespace-only, over-length) and found the server *does*
enforce these rules, then explicitly said so: *"TD-2026-004 appears to be WRONG or outdated."*

This is not just "the oracle mentioned it once and the model parroted it" - it's the same specific,
falsifiable claim being independently tested and independently refuted, four separate times, by
four different model runs that never saw each other's output. **This finding is structurally
impossible in the without-oracle arm** - there's no `TD-2026-004` claim in that arm's evidence to
test in the first place. That's the real shape of the oracle's value here: not more bugs, but a
concrete, falsifiable, project-grounded claim to check against live behavior, reliably surfaced
and reliably tested.

## Result 4: awareness of the one real open risk - total, but never actually exercised

| Theme | Without oracle | With oracle |
|---|---|---|
| Ownership gap (`R-2026-006`) named | **0/5** | **5/5** |
| Content-validation claim (`TD-2026-004`) named | 0/5 | 5/5 |
| XSS/sanitization (`AC-SEC-03`) named | 0/5 | 5/5 |
| Unbounded growth (`R-2026-007`) named | 0/5 | 2/5 |
| Frontend integration gap (`KI-2026-008`) named | 0/5 | 3/5 |
| In-memory/no-persistence (`TD-2026-001`) named | 5/5 | 5/5 |
| CORS (`AC-SEC-01`) named | 2/5 | 2/5 |

`R-2026-006` - the one real, currently-open, high-severity risk on this feature (any client that
knows a note id can modify or delete another session's note, with zero ownership check) - is named
by ID in **every single with-oracle trial and zero without-oracle trials**. That's as clean a
split as this kind of comparison produces.

**Important honest caveat, though**: in every with-oracle trial, it's named only as an *untested
gap*, never as something a test actually exercised or confirmed. The notes API has no
session/auth concept anywhere in its request schema - there's no field to vary to construct a
genuine "does session B's client see session A's note" test. So the oracle reliably raises the
right question, five for five, but doesn't (and structurally can't, without a harness change to
simulate multiple sessions) actually close it. `TD-2026-001` (in-memory, no persistence) shows the
opposite pattern - 5/5 in *both* arms, because that fact is already stated directly in the
`ENDPOINT_SPEC` both arms receive, so the oracle adds nothing there; it only shows a gap where the
plain spec is silent.

## Honest limitations

- N=5 per arm - no statistical test is justified at this size, though the 0/5 vs 5/5 splits above
  are about as stark as they come.
- Theme "mentioned" is a keyword/ID-citation tally, not a judged-correctness call, and it does not
  distinguish "raised as a gap" from "actually tested" - Result 4's caveat matters more than the
  raw counts.
- I scored this myself, not blinded to which arm produced which trial.
- Skeptic satisfaction (Result 1) genuinely shows nothing at this budget - don't read a null result
  as "the oracle doesn't help"; it means this particular outcome measure isn't sensitive at 21
  tests for this SUT.

## Bottom line

On raw bug yield, nothing - once you strip out the model's own self-corrected miscounting, neither
arm found a real behavioral defect. But the oracle library did two things reliably and repeatably
that the plain endpoint spec alone never produces: it gave the Driver a specific, falsifiable claim
from the project's own documentation to test and refute (4/5 trials, a genuine and useful finding
about stale internal docs), and it raised the one real open security gap on this feature by name in
every single trial, where the baseline never mentioned it once. Neither result is "the oracle finds
more bugs" - it's "the oracle makes the Driver ask better, more specific questions, consistently,"
which is a real effect even though this run couldn't push it all the way to closing the ownership
gap itself.
